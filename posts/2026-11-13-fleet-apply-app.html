Proposal · Self-service fleet apply

A web app applies YAML to the fleet. No person needs cluster-admin.

An engineer completes a form or pastes YAML. The engineer selects one cluster or a set of clusters. The app does the checks, gets a second approval, and runs oc apply with a limited service account. Then the app records the result.

This is a prototype. It does not apply changes. The 1,040 clusters are sample data. The rollout is a simulation. The user is a.engineer.

      What the app replaces
      
  
      
    
      Permanent cluster-admin
      Fleet apply app
      
    
      Permitted actions
      All actions. This includes RBAC changes and namespace deletion.
      Only the resource kinds on the allowlist. Only in namespaces that the platform does not own.
      
    
      Checks before the change
      No check is mandatory. The person makes the decision.
      A YAML check, an allowlist check, a server-side dry-run, then a second approver.
      
    
      Record
      Each cluster has API audit entries. The reason and the approval are in other systems.
      One record for each change: ticket, requester, approver, manifest, and the result for each cluster.
      
    
      Changes to many clusters
      A script loop on the laptop of an engineer.
      Select the clusters by label. The canary cluster is first. Then the waves follow. A failure stops the rollout.
      
    
      Write access
      Each admin has write access to each cluster at all times.
      Limited service accounts have write access. Engineers keep read access.
      
  
      

      


      
  
      What the system does after the form
      
  
        
    
      1. The app identifies the engineer through SSO. The app does not give a cluster credential to the engineer.
        2. 
    
      2. The app commits the manifest to Git with the ticket number. Git keeps each version of the YAML. You can revert a version.
        3. 
    
      3. The server does the same checks again. Then the server runs oc apply --dry-run=server on a sample cluster.
        4. 
    
      4. After approval, a runner applies the manifest in waves. Each action class has its own service account with a narrow ClusterRole. No service account is cluster-admin.
        5. 
    
      5. Each wave must pass the health checks. The system writes the results to an append-only store and to the ticket.
        6. 
    
      6. An admission policy in each cluster refuses or flags the writes that did not come from the app.

      Questions and answers
      
  
      
    
      What do we do if there is an outage at night?
      Keep a break-glass procedure. The access has a time limit and an incident number. The system sends an alert. A reviewer examines the access after the incident.
      
    
      Does the app become the new cluster-admin?
      No, if the design is correct. Each action class has its own limited service account. A different team owns the allowlist. The admission policy is a second barrier. Thus one security failure has a small effect.
      
    
      What if a change is not on the allowlist?
      The app refuses the change and gives the reason. A new action class must have a review before the team adds it. The refusals show which action classes to add next.
      
    
      Can engineers continue to find faults?
      Yes. Engineers keep read access to all clusters. Only the write actions move to the app.
      
  
      

      


      
  
      The decision
      
  
      Approve a pilot. The pilot includes this app, an allowlist of our most frequent changes, and a break-glass procedure. The pilot runs on clusters that are not production clusters. Measure two values: the number of permanent cluster-admin grants that we remove, and the percentage of changes that have a full record.
